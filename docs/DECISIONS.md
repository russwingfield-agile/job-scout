Also unverified: `salary` / `salaryType` text on `jobs/{id}`, `applicationCount` vs `applications`, `datePosted` vs `date`. The shared `ReedJobDetailsSchema` is loose so a mismatch degrades parsing rather than failing.
- **`ReedJobDetailsSchema` lives in `packages/shared`** (not an adapter) because `core/normalise.ts` must stay free of adapter imports. `NormaliseContext` gained `now: Date` (fallback posted date) so normalisation stays pure.
- **New setting `working.hoursPerDay` (default 8)** for annualising hourly rates; M1 only had `workingDaysPerYear`.
- **Pay parsing rules** (`core/parse/pay.ts`):
  - Confidence is `high` (explicit period), `medium` (period inferred from size), `low` (amount but period unknowable) or `none`.
  - Inference follows SPEC §4.4: ≥ £10,000 is a year; below £2,000 is a day rate for contract/temp/unknown — and, my refinement, an hourly rate below £100; permanent amounts under £2,000 stay `unknown`; £2,000–£9,999 is `unknown`.
  - "up to £X" gives max only. A single figure sets min = max. A reversed range is swapped. A k-suffixed partner scales a bare number under 1,000 ("80-95k").
  - Bare numbers ("2 days a week") count only when a period keyword follows them directly, so day counts and years of experience are not read as pay; `£`/`k` amounts may find their period within ~25 characters.
  - Reed's structured min/max are used only when the text has no amount. A rate quoted in the advert body is used only with an explicit period (`high`), never from magnitude, to avoid "£50m turnover" false positives.
- **IR35:** contradictory wording ("outside IR35 … some roles inside IR35") and undecided wording ("TBC") return `unknown` so the hard filter passes the job (SPEC §7.1). PAYE/umbrella leans inside (`medium`); "Ltd company" leans outside (`low`). Permanent roles get no IR35 value.
- **Work mode:** stated office days win over keywords (≥ 5 days = onsite, otherwise hybrid); monthly figures are converted to days per week (1 day/month ≈ 0.23). Plain "onsite" alone is `low` confidence. These regexes are a first pass for the LLM to refine.
- **Titles:** "Lead" counts as seniority only as the first word, so "Delivery Lead" keeps its role word. `tokenSetRatio` follows the fuzzywuzzy method (subset ⇒ 1.0); the dedupe step (M6) also requires cosine ≥ 0.92.
- **Coverage gate.** `pnpm test:coverage` (part of `pnpm check`) enforces 100% on `core/parse/**` and ≥ 90% elsewhere in `core/`, measured on the `worker-unit` project (the Workers pool does not support v8 coverage). Coverage config must live in the root `vitest.config.ts`.
- **Parser constants.** The magnitude thresholds (10,000 / 2,000 / 100 / 1,000) are named constants in `pay.ts`, not settings: they define how a number is read, not how a job is ranked.

Verified with a real key (Basic auth, key as username, empty password). Recorded responses are in `apps/worker/test/fixtures/reed/real/` (recorded with `scripts/record-reed-fixture.mjs`; no key or contact details in them). The earlier synthetic fixtures in `fixtures/reed/*.json` are kept for parser edge cases.

- **Confirmed M2 assumptions:** dates are day-first `dd/MM/yyyy`; `jobs/{id}` has `salary` ("£640.00 - £850.00 per day"), `salaryType` ("per day" / "per annum"), `datePosted`, `contractType` ("Contract" / "Permanent"), `externalUrl`, `fullTime`/`partTime`, and `yearlyMinimumSalary`/`yearlyMaximumSalary` (Reed annualises days × 260).
- **Search shape:** `{ results[], ambiguousLocations[], totalResults }`; each result has `jobId, employerId, employerName, jobTitle, locationName, minimumSalary, maximumSalary, currency, expirationDate, date, jobDescription (truncated snippet ending "..."), applications, jobUrl`. Full HTML is only on `jobs/{id}`.
- **Unknown job id returns HTTP 200 with a blank record** (`jobId: 0`, all other fields null), not a 404. `ReedAdapter.details` converts this to a non-retryable `NOT_FOUND`.
- **Nulls:** text fields can be `null`; the shared schemas read them as `''`.
- **Bad key → HTTP 401** with an empty body (non-retryable). No rate-limit headers were observed; limits remain undocumented, so the daily budget (default 900) and per-run cap (60) stay as the safeguard.
- **Paging:** `resultsToTake` is capped at 100 (101 returns 100); `resultsToSkip` past the end returns an empty page with the real `totalResults`. A broad query ("project manager", London) has ~2,600 hits, so `maxPagesPerQuery` (3) means only the newest ~300 are seen.
- **Filters:** `contract`, `permanent`, `temp` OR together; none sent means all types; `contract=false` is ignored (so only `true` flags are sent, and all three = none). `distanceFromLocation` changes the result set materially (default is narrower than 25 miles).
- **`minimumSalary`/`maximumSalary` units are not stated** (a contract can carry 640–850 as day rates or 50,000 as an annual figure). Pay is parsed from the `salary` text first; the numbers are only a fallback, and `minimumSalary` is sent as a search filter for permanent-only queries.
- **`applicationCount` on `jobs/{id}` was 0** where the search result showed 21–83 `applications`; treat the details value as unreliable. (Not fixed: low value, and normalisation has no access to the search hit.)
- **Parser fix found by real data:** `salary` already contains the period, so `salaryType` is appended only when the text does not already include it (previously produced "per day per day").
- **Decisions:** `SourceAdapter` takes an optional `{ runId }` so call records can be attributed to a run; `ReedClient` reports every request, including failures and timeouts, to a recorder that writes `source_calls` and increments `usage_daily.reed_calls`; recorder failures never fail the request. Network errors, timeouts, 429 and 5xx are retryable; 401/403, other 4xx and unexpected response shapes are not.
- **Recorder script is `.mjs`**, not `.ts` as the plan says, so it runs with plain Node and needs no type-checking setup.
- **Deployment:** the deployed Worker has no `REED_API_KEY` yet. Set it before M5 with `wrangler secret put REED_API_KEY --config apps/worker/wrangler.jsonc`.

## M4 — CVs, profiles, embeddings

**Workers AI facts (from Cloudflare docs, checked 2026-11-20 — NOT yet exercised against the live service):**
- `llama-3.3-70b-instruct-fp8-fast` costs 26,668 neurons per million input tokens and 204,805 per million output tokens (verified, pricing page). The rates for `llama-3.1-8b-instruct` (25,608 / 75,147) and `bge-base-en-v1.5` (6,058 input) are from memory and **unverified**; they are marked as such in `config/neuronRates.ts`. Unknown models are costed like the 70B so the budget never under-counts.
- `env.AI.toMarkdown([{ name, blob }])` returns an array of `{ name, format: 'markdown' | 'text' | 'error', data, tokens, error? }`. The docs spell the MIME field both `mimeType` and `mimetype`; the adapter does not read it.
- JSON mode: `response_format: { type: 'json_schema', json_schema: <schema> }` on a non-streaming call; the schema is passed directly under `json_schema`. `run()` returns `{ response, usage: { prompt_tokens, completion_tokens } }`, and `response` can already be a parsed object, so the adapter accepts a string, an object, or the OpenAI chat shape.
- The adapters were written to these documented shapes and tested against fakes of them. **Exit criterion still open:** upload real CVs in dev with remote AI and confirm summaries, embeddings and profiles (needs `wrangler login` and the Vectorize/R2 resources).

**Decisions:**
- **R2 and Vectorize bindings are optional at runtime.** `createContainer` builds `R2Blobs`/`VectorizeStore` only if `env.CVS`/`env.VEC` exist; otherwise those ports fail with `NOT_CONFIGURED` (HTTP 503) naming what is missing. This lets the code deploy before the resources exist (a missing binding in `wrangler.jsonc` would otherwise fail the deploy). Uploads fail before anything is stored.
- **A CV is never lost to an AI failure.** Storage and the row are written first; text extraction, summary and embedding each degrade to a `warnings[]` entry, and "Re-analyse" retries them. An unreadable document becomes a CV with empty text so the user can paste it in. A new profile falls back to the CV label as its only job title when there is no summary.
- **`structured()`** (plan §2.5) is in `ai/structured.ts`: budget check → primary model (cheap model if >80% of the neuron budget is spent) → one repair call quoting the error → one fallback-model call → `{ ok: false, reason: 'budget' | 'invalid_output' | 'llm_error' }`. Every call is counted in `usage_daily` using reported token usage or a chars/4 estimate. `reason: 'budget'` lets M7 mark work `deferred`.
- **Upload validation:** declared type must be PDF/DOCX and the first bytes must agree (`%PDF-` / `PK\x03\x04`); a generic `application/octet-stream` defers to the sniffed type. Size limit is `settings.cvs.maxUploadBytes` (5 MB), enforced in the service; a fixed 16 MB body cap protects memory before the file is read. Stored file names are sanitised.
- **Active CVs:** max `settings.cvs.maxActive` (4); both uploading and re-activating over the limit return 409. Inactive CVs keep their vector but must be excluded by scoring (M5/M7).
- **Embedding model is fixed at container construction** from `DEFAULT_SETTINGS.models`: changing it would invalidate every stored vector, so it is deliberately not hot-swappable through Settings.
- **The web app uses `fetch` + shared Zod schemas, not the Hono RPC client** the plan names: importing the Worker's types into the web project would pull Cloudflare globals into a DOM project. Response shapes are still validated against the shared schemas, so client and server cannot drift silently.
- **Embedding text** is the summary's headline, seniority, skills, sectors and roles followed by the CV text, truncated to 2,000 characters (≈500 tokens, SPEC §3.3).

## M5 — Ingest pipeline (schedule → fetch → process)

- **Cloudflare free-plan limits matter here (docs checked 2026-11-20).** Workers Free gives 10 ms of CPU per invocation (Cron Triggers are listed at 10 ms on Free; the limits page gives no separate figure for Queue consumers), 50 subrequests per invocation, and Queues allow 10,000 operations/day with 24 h retention. Consequences baked in: **one message per invocation** (`max_batch_size: 1` for both queues, so CPU is not summed across jobs), modest consumer concurrency, and per-message work kept small. **UNVERIFIED:** whether a `process` message fits in 10 ms CPU on Free. Time spent waiting on Reed/AI/D1 does not count, but parsing, Zod and Drizzle do. If runs show "exceeded CPU" errors in the Runs page, the remedies are the Workers Paid plan ($5/month; 30 s CPU) or trimming work per message. Queue operations: ~3 per message (write, read, delete), so a run of ~300 jobs ≈ 1,000 ops and three runs a day stay under 10,000, but a busier day could hit the cap.
- **`fetch` messages carry `profileIds[]`, not one `profileId`** (plan §2.3). Identical queries from different profiles are merged into one Reed call (the budget is limited) and every hit is credited to all of those profiles (`job_profile_hits`).
- **Exactly-once counters (plan §2.4), made atomic.** Both *enqueueing* and *completing* a message move `runs.pending_ingest` through one D1 batch: "adjust the counter unless this key is already in `processed_messages`", then "record the key". Keys: `enq:process:{run}:{job}`, `done:process:{run}:{job}`, `enq:fetch:{run}:{query}:{page}`, `done:fetch:...`. A redelivered message or a job found by two queries cannot move a counter twice or be queued twice (tested with every message delivered twice). `processed_messages` is the only bookkeeping; the phase change `ingest → scoring` is a conditional UPDATE so exactly one handler advances the run.
- **Failure contract.** Transient errors (network, 429, 5xx, unknown exceptions) → `retry` with backoff `min(300, 10·2^n)s + ≤20% jitter`; permanent errors or the final attempt (`QUEUE_MAX_RETRIES = 3`, must equal `max_retries` in wrangler.jsonc) → the error is written to `run_errors` and the message is *completed anyway*, so a failing message never leaves a run waiting. Invalid messages are logged and acked. Messages that are lost outright (a crash between claiming and sending) are caught by stale-run recovery: runs not finished after `budgets.staleRunMinutes` (30) become `stale` at the next hourly tick.
- **New column `jobs.stage` (`ref` → `detailed` → `processed`)** (migration 0002) makes processing resumable: a retry after the advert was fetched reuses the stored `raw_json` instead of spending another Reed call, and reuses the existing group instead of creating a second one. "Re-running immediately adds ~0 new jobs" falls out of this: only jobs still at `ref` are queued.
- **`SourceAdapter.search` returns `hasMore`** (SPEC §4.3) so the pipeline pages without knowing Reed's page size. Paging continues only while the page produced new work and `maxPagesPerQuery` allows.
- **Hard filters (SPEC §7.1) as implemented:** employment type, exclude keywords (whole-word), pay below the profile minimum compared on a *yearly* basis (day rate × working days; hourly × hours × days; a contract quoted as a salary is compared the same way), inside-IR35 for `outside_only` profiles, work mode when known and not in the profile's list, and the global blocklist. Unknown values always pass. A job passes if it passes for any profile that found it; filtered jobs still get a group (status `filtered`) so they stay visible with their reason.
- **Prefilter score** = clamp(sim_norm + bonuses + feedback_adj, 0, 100) per SPEC §7.2; the title bonus reuses `dedupe.titleTokenSetRatio` as its fuzzy threshold.
- **Not done in M5 (by design):** de-duplication (M6: every job gets its own group; `dupes` stays 0) and LLM selection/scoring (M7: `selectForScoring` just finishes the run).
- **Bug found by tests:** the Runs list's Reed-call and error counts were always 0 — drizzle printed the outer `runs.id` unqualified inside a correlated subquery, so it compared the subquery table's own `id`. The subqueries now name `runs.id`.
- **Deploying the pipeline needs, before it runs for real:** the queues (`fetch-q`, `process-q`, `job-scout-dlq`) created in the dashboard, their bindings enabled in `wrangler.jsonc`, **Queues → Edit** on the deploy token, and `REED_API_KEY` stored as a Worker secret. Until then "Run now" answers 503 NOT_CONFIGURED, and a scheduled tick records a failed run saying so.
- **Queues enabled (2026-11-20).** `fetch-q`, `process-q` and `job-scout-dlq` were created by the owner in the dashboard; the producers/consumers are now active in `wrangler.jsonc` (batch size 1, concurrency 2 and 5, 3 retries, dead-letter queue). `score-q` arrives with M7.

### M5 follow-up — first live run (2026-11-20)

- **What the first real run showed:** 1,419 adverts fetched, 1,043 "new", 60 Reed calls, 354 errors. The 60 was the per-run cap I had set from the SPEC's steady-state estimate; on an empty database every advert Reed returns is new, so everything past the cap was refused and recorded as an error. Nothing was lost (those jobs stayed "seen" and unprocessed) but the design was wrong for a first run.
- **Fixes:**
  - **Age window.** New setting `ingest.maxAgeDays` (default 7). Adverts posted before that are recorded as `too_old` and never fetched in full (each full advert costs a Reed call, and the Inbox is about recent jobs). Counted as `tooOld`.
  - **Budget-aware queueing.** `fetchPage` queues only as many adverts as the run and daily Reed budgets can pay for (cap − calls made − adverts already queued − 1 held back for a next page), newest first. The rest are counted as `deferred`, not errors.
  - **Backlog pickup.** `startRun` also queues jobs left at "seen" by earlier runs, newest first, within the budget left after reserving the run's searches (`queries × maxPagesPerQuery`). Deferral therefore never depends on a later search happening to rediscover a job.
  - **Late exhaustion is deferral too:** a `process` message that finds the budget spent leaves the job at "seen" and counts it as deferred instead of raising an error.
  - **`budgets.reedCallsPerRunCap` default 60 → 250** (three runs a day stay inside the 900 daily budget).
- **ASSUMPTION (unverified):** Reed returns search results newest-first (or close to it), which is why "newest first within a page, stop paging when a page yields no work" is sound. If results are ranked by relevance instead, older matching jobs could be revisited before newer ones; revisit if the shortlist looks stale.
- **Temporary shortlist view (plan "early-value shortcut").** `GET /api/groups?show=shortlist|filtered&limit=` and a Shortlist page list jobs by first-pass similarity score, with the filtered view explaining why each was hidden. Replaced by the full Inbox in M8. The nav item "Inbox" is labelled "Shortlist" until then.
- **Test harness:** `FakeSource` now records calls through the real recorder, so Reed budget accounting in tests matches production.

### Location fix (2026-11-20)

- **Problem:** a profile location of "Remote" searches Reed with no place restriction, which returns jobs from the whole country; nothing then required those jobs to be remote (SPEC §6.2 says it should), so the shortlist showed jobs from many locations.
- **Fix:** `job_profile_hits.scoped` (migration 0003) records whether a place-restricted search found the job. A job found only by the unrestricted search must itself be remote (`not_remote` filter; unlike other rules, an unknown work mode does not pass here). A scoped find always wins. Existing hits default to scoped, so jobs already in the database from before this change are not re-checked.
- **Still to do:** a "clear found jobs" action to start fresh after profile changes; an integration test of the London + Remote scenario through the whole pipeline (unit tests of the rule exist).

### M7 — selection, AI assessment, final score (2026-11-20)

- **Selection (`pipeline/selectForScoring.ts`).** Looks at every group still `prefiltered` or `deferred` (not only this run's, so jobs that miss out one run are not forgotten). Deferred groups go first, then first-pass candidates by score, up to `budgets.maxLlmPerRun`. Candidates under `thresholds.prefilterMin` become `below_threshold`; candidates above it that did not fit stay `prefiltered` for the next run (the plan said "rest → below_threshold", which would have made them unreachable).
- **`below_threshold` and the Shortlist page.** The temporary Shortlist shows `prefiltered`, `pending_llm`, `deferred` and `new`. Low first-pass matches (`below_threshold`) are therefore hidden from it; the "More" filter for them arrives with the M8 Inbox.
- **Score queue.** New `score` message and `score-q` (producer `SCORE_Q`, consumer batch 1, concurrency 2, 3 retries, same dead-letter queue). Completion decrements `runs.pending_score`; the handler that reaches zero calls `finaliseRun`. A redelivered message finds the group no longer `pending_llm` and does nothing, so the model is never paid for twice. A message that fails permanently sets the group to `deferred` (picked up by a later run) and the run still completes.
- **Bus now needs all three queues.** `createContainer` only builds the real bus when `FETCH_Q`, `PROCESS_Q` and `SCORE_Q` are all bound, otherwise starting a run answers 503 NOT_CONFIGURED. `score-q` must exist before the M7 deploy.
- **`assessGroup`** (`pipeline/assessGroup.ts`, also used by `POST /api/groups/:id/rescore`): prompt `assess@1` (job text ≤ `assessment.maxJobTokens`, all CV summaries, full text of the `assessment.fullTextCvCount` most similar CVs each ≤ `maxCvTokens`, the finding profiles' preferences) → `structured()` → checks → stores the assessment → fills job facts → final score.
  - Checks (`core/assessment.ts`): contact email/phone must appear in the advert (phone compared by digits only), otherwise null; `best_cv_id` must be an active CV, else the best-scoring valid CV, else the most similar CV; scores for unknown CVs dropped.
  - Facts: the model's employment type, work mode, IR35, contract length and pay are used only where our parser found nothing (SPEC §7.3). Annualised pay is recomputed when pay is filled in.
  - Final score (`core/scoring/final.ts`): `round(0.75·fit + 0.20·sim_norm + 0.05·freshness) + feedback_adj`, clamped 0–100, weights from settings.
- **Failure handling.** Budget exhausted → group `deferred` (run) or untouched (manual rescore, which answers 429). Invalid output / model error after the repair and fallback attempts → a `failed` assessment is stored, the group still moves to `new` with no final score, and the list falls back to its first-pass score and says the AI could not assess it. `assessments.result_json` became nullable for this (migration 0004).
- **List ordering** is by final score when there is one, otherwise first-pass score (`coalesce`), then newest.
- **Clean-up (`pipeline/cleanup.ts`).** After the last scheduled run of the local day (`isLastSlotOfDay`, so it follows the configured schedule rather than a hard-coded 17:00), filtered groups first seen more than `retention.filteredDays` ago are deleted with their postings, hits, similarities, assessment and vectors. A clean-up failure is recorded as a run error and never stops the run finishing. Too-old placeholder jobs (no group) are kept so they are never fetched again.
- **Not done in M7:** the evaluation harness `scripts/eval-assess.ts` and its fixtures (needs real model calls and hand-labelled job/CV pairs; to do before trusting scores), and a rescore button in the UI (the endpoint exists; M8 adds the drawer). Neuron costs for 8B are still unverified (see neuronRates.ts).

### M6 — de-duplication (2026-11-20)

- **Deviation from the plan (task 2):** instead of `vectors.query` (which scans every stored vector, too much CPU for a Free-plan invocation), `findDuplicate` first selects recent passing postings from D1 (last `dedupe.lookbackDays`, at most 500), applies the cheap test (title token-set ratio ≥ `titleTokenSetRatio`, or pay bands within `payBandTolerance` and the same city), keeps the best `dedupe.topK` by title score, and only then loads those few vectors and applies `cosine ≥ dedupe.similarity`. Same rule as SPEC §8.2, far less work.
- **Only jobs that pass the hard filters are compared** (they are the only ones embedded). Filtered postings keep a group of their own, shown under "show filtered".
- **Joining:** the posting attaches to the matching group; the group is not re-scored or re-assessed (assessment is per group), `last_seen_at` moves, `new_postings_since_action` goes up if the user has already acted on the group, and the canonical posting is recomputed (pay, then IR35 known, then longest description, then earliest). Run counts show `dupes`.
- **Race:** after a new group is created and its vector stored, `findDuplicate` runs again; if another group is the same role and older (first seen, then id), `groups.mergeInto` folds ours into it in one D1 batch (postings, vector tags moved; similarities, assessment and the group row deleted).
- **Test fixtures:** each fixture advert now carries id-specific words so unrelated fixtures are not mistaken for duplicates; duplicate tests use identical long descriptions.

### M9 — cover notes and feedback learning (2026-11-20)

- **Cover notes.** `POST /api/groups/:id/cover-note` (`{cvId?, tone, kind}`) and `GET /api/groups/:id/cover-notes`. Prompt `coverNote@1` (UK spelling; facts only from the CV; mirror 3–5 advert terms; banned clichés; one call to action; plain text). Written through `ai/coverNote.ts`, the "cover-note helper" the architecture allows besides `structured()`: budget-checked first (429 when the day's allowance is spent), uses the fallback model above 80% of the budget, records usage. The reply is tidied (`cleanNote`) and held to the limit (`limitWords`: cut at the last full sentence that fits) because models overrun. Limits and token caps are a new Settings section `coverNotes` (200 words / 90 words / 3,000 tokens each for job and CV). Drafts are saved in `cover_notes`; regenerating keeps history (newest first, ordered by insertion so same-millisecond drafts stay in order). Edits to a draft happen in the browser only (copy it out); they are not saved.
- **Feedback learning (`core/scoring/feedback.ts`).** At prefilter time each new job gets `feedback_adj` (−10..+10) with plain-English reasons: ≥3 agency-spam skips from the same employer −10; applied to the same employer before +5; ≥0.88 similar to your last 50 applied/shortlisted jobs +5; ≥0.90 similar to your last 50 "not my skills" skips −5. Stored on the group (`feedback_adj`, `feedback_reasons_json`), included in the first-pass and final scores, shown in the job drawer. "Same hiring company" is approximated by employer name (the assessment's extracted hiring company is only known later). Vectors are read only when you have acted on something, to stay inside the Free-plan CPU limit.
- **Suggestions.** `GET /api/suggestions`, `POST /api/suggestions/apply|dismiss`. From skips in the last `feedback.suggestionWindowDays` days, at least `suggestionMinSkips` per profile: low-rate skips that all sit under the minimum + `suggestionRateBuffer` → raise the minimum day rate (rounded up to £25 above the highest skipped rate); location skips → halve the search radius (floor 5 miles); inside-IR35 skips → outside IR35 only. Suggestion ids are deterministic so a dismissal sticks (stored under the settings key `dismissedSuggestions`, ignored by the settings merge). Shown as cards at the top of the Inbox, since there is no Settings page yet.
- **UI:** a Cover note tab in the job drawer (`c` in the Inbox opens it), editable draft with word count and Copy, earlier drafts below; suggestion cards; score-adjustment reasons in the drawer overview.

### M10 — hardening (2026-11-21)

- **Already in place from earlier milestones:** Cloudflare Access JWT verification on every `/api` route (fails closed; `OWNER_EMAIL` allow-list when set; `DEV_BYPASS_AUTH` only when `ENV=dev`), deploy-from-main with migrations (`.github/workflows/deploy.yml`), retention clean-up (M7).
- **Security headers.** API responses (including errors) always carry `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, a lock-down CSP (`default-src 'none'; frame-ancestors 'none'`) and `Cache-Control: no-store` (`http/middleware/security.ts`). Pages and scripts get `apps/web/public/_headers` (CSP `default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'; frame-ancestors 'none'`, nosniff, no-referrer, `X-Frame-Options: DENY`), which Workers static assets apply to everything they serve. ASSUMPTION: the Access sign-in redirect is unaffected (it happens before our Worker).
- **Request limits.** JSON requests over 1 MB are refused with 413 (judged by `Content-Length`, which Cloudflare always sets for ordinary requests); CV uploads keep their own limit from Settings. Zod string limits cover notes (5,000), confirmation phrase, etc.
- **Advert HTML** is sanitised before it is stored (`core/sanitiseHtml.ts`): allow-list of formatting tags with no attributes, links only with `http(s)` and `rel="noopener noreferrer"`, scripts/styles/frames/comments removed with their contents. It is a small purpose-built sanitiser, not a full HTML parser; the UI never renders this HTML (it shows plain text), so this is defence in depth.
- **Delete all data** (`DELETE /api/data`, body `{"confirm":"DELETE EVERYTHING"}`; 409 while a run is working): removes every job, assessment, note, run, usage count, CV with its R2 file, search profile and vector (CV and job vectors by id, so Vectorize would work too). Settings are kept. Surfaced in a Danger zone on the new Settings page, which also edits scan times, per-scan AI limit, first-pass cut-off, age window and the blocklist.
- **Volume check:** an integration test seeds 2,000 groups and asserts the Inbox query returns the best 100 in order, with the right total, in under 2 s in the test runtime. The plan's `EXPLAIN QUERY PLAN` p95 < 300 ms check against real D1 has not been done; revisit if the Inbox feels slow.
- **Not done:** Vectorize cleanup is only by id (no "delete by metadata"), and no end-to-end Playwright/Lighthouse runs (see M8).
